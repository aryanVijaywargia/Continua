This page is the honest line between the parts of Continua you can rely on today, the
parts that work but are still **preview**, the parts that exist as **stubs** with real
files in the repo, and the parts that are only **planned**. Nothing in the planned section
has an implementation package in the repo yet.

## Shippable today

These surfaces have real implementations, end-to-end tests, and at least one production
shape. Everything in the rest of this docs site assumes they exist.

| Area | What's there |
| --- | --- |
| **REST ingest** | `POST /v1/ingest` (sync + true-async with durable batches and idempotency), `GET /v1/ingest/batches/{id}` for polling |
| **REST reads** | Traces, spans, span events / merged timeline, sessions, session narrative, session compare |
| **Project management** | Create / update / delete / rotate-key endpoints under `/api/projects`, API-key auth via `X-API-Key` |
| **Auth0 operator login** | Optional bearer-auth for the debugger UI gated by `AUTH0_ALLOWED_EMAILS` |
| **Public demo mode** | Read-only seeded project for evaluations |
| **Python SDK** | Decorators, context managers, batching, sync / async / server-default ingest modes, polling helpers |
| **Debugger UI** | Traces list, trace detail (waterfall, span tree, timeline, payload inspector), sessions list / detail / compare, settings, command palette, theming |
| **Engine schema + control + console** | Postgres engine schema with reversible migrations, `/v1/engine/*` control endpoints (preview-gated), and the runs console UI. The execution runtime is **preview**, see below |
| **Background jobs** | River workers for ingest, rollups, and payload cleanup |
| **Self-hosting** | Single Go binary + Postgres, env-only config, embedded SPA, `continua migrate` + `continua-engine migrate` |

## Preview: works, but not production-hardened

These have real implementations and end-to-end tests, but carry caveats that keep them out
of "shippable today." Use them, just not on a production-critical path.

### Durable engine workflow execution

The `continua-engine` worker runtime executes **Go-defined** workflows end-to-end:

- It claims runs, schedules activities, fires timers, delivers signals, spawns child
  workflows, and replays event-sourced history to drive each run to a terminal result.
- Activities retry with exponential backoff; runs and activities recover across process
  restarts via leases + history replay (covered by the restart suite in
  [`engine/cmd/continua-engine/`](https://github.com/aryanVijaywargia/Continua/tree/main/engine/cmd/continua-engine)).
- Run state is projected into `public.traces` for the [engine runs](/debugger/engine-runs)
  console.

Preview caveats:

- **Go-only authoring**: no TypeScript/Python SDK for authoring workflows yet.
- **No production definition loading**: definitions register through the Go runtime that
  starts workers; there's no multi-tenant register-and-version path yet.
- **Preview REST sunset**: `X-Continua-Engine-Preview: 1` is optional and deprecated for mutating (POST) endpoints; all `/v1/engine/*` endpoints still require `ENGINE_PUBLIC_API_ENABLED=true`. See the [documented GA path](/concepts/engine-foundation#path-to-ga-for-v1engine).

See [Engine foundation](/concepts/engine-foundation) for the full picture.

## Stubbed: real files, not yet a supported product path

These have real files in the repo, but they are not feature-complete. Don't depend on
them; the surface may change before they ship.

### TypeScript SDK

[`sdks/typescript/`](https://github.com/aryanVijaywargia/Continua/tree/main/sdks/typescript)
has real build scaffolding: `package.json`, `tsconfig.json`, `.eslintrc.json`,
`tsup.config.ts`, and one test file. The only source file is a placeholder
[`src/index.ts`](https://github.com/aryanVijaywargia/Continua/tree/main/sdks/typescript/src/index.ts):
it exports `VERSION` and a `ContinuaClient` whose only member is a `baseUrl` getter,
preceded by a TODO comment. There are no generated OpenAPI types, no fetch calls, no batching,
no decorators, and no ingest helpers yet.

**Use the Python SDK** if you need real instrumentation today. TypeScript instrumentation
is on the roadmap; tracking the work in the repo is the most reliable signal.

## Planned: not implemented yet

There is no implementation package for these capabilities in the repository. Tracking work
on GitHub is the most reliable signal.

### Live WebSocket runtime

The contract under [`contracts/websocket/events.ts`](https://github.com/aryanVijaywargia/Continua/tree/main/contracts/websocket)
defines a live-update event schema. The debugger UI does **not** consume it today: trace
detail is polling-based via `GET /api/traces/{id}/events`. There is no server-side
WebSocket implementation yet.

### Proxy capture

An HTTP-proxy capture mode that records LLM / tool calls without code changes to the agent
is planned. It has no implementation in the repository today. Instrument with the Python
SDK instead.

### Trace-replay execution

Re-executing recorded runs against new code or model versions is planned. Not implemented.
This is distinct from engine crash-recovery workflow replay, which is implemented. Use
[session compare](/debugger/session-compare) for offline diffing.

## What we'd reach for next

Rough ordering, subject to change as feedback comes in:

1. Finish the TypeScript SDK to parity with Python for trace / span / session instrumentation.
2. WebSocket runtime so the trace detail page can drop polling.
3. Graduate the durable engine from preview: multi-tenant workflow definition loading, non-Go (TypeScript/Python) workflow authoring, and the [documented GA path for `/v1/engine/*`](/concepts/engine-foundation#path-to-ga-for-v1engine).
4. Proxy capture for zero-code instrumentation.
5. Platform trace-replay execution as a layer on top of durable engine workflows.

If you have a strong opinion on the order, open an issue on
[GitHub](https://github.com/aryanVijaywargia/Continua/issues): we read every one.
