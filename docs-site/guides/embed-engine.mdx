---
title: "Embed the engine"
description: "Run the preview durable engine inside a Go program with your own workflow and activity registries."
---

The engine runs as an embedded Go library. Your program registers workflow
definitions and activity handlers, then starts the same worker loop that powers
`continua-engine serve`. This is the supported way to run your own workflows;
`continua-engine serve` runs only the built-in demo definitions.

For a step-by-step setup from an empty directory, including the Go module, the platform
server, and the first run, see [Run your own workflows](/guides/run-your-own-workflows). This page is the reference
for `runtime.Options`.

<Warning>
  The durable engine is still preview. Workflow authoring is Go-only, and runs of
  your definitions start through the preview control plane (`POST /v1/engine/runs`,
  which needs `ENGINE_PUBLIC_API_ENABLED=true` on the platform server).
</Warning>

## Register definitions and handlers

Use `github.com/continua-ai/continua/engine/pkg/runtime`. `runtime.OptionsFromEnv` reads
the same `ENGINE_*` environment settings as `continua-engine serve` and returns them as
`runtime.Options`. Add your definitions and handlers, then build and run the runtime:

```go
options, err := runtime.OptionsFromEnv(os.Stderr)
if err != nil {
    return err
}
options.Workflows = []workflow.Definition{
    {
        Name:    "examples.greeter",
        Version: "v1",
        Run:     runGreeterWorkflow,
    },
}
options.Activities = map[string]runtime.ActivityHandler{
    "examples.greet": greetActivity,
}
rt, err := runtime.New(options)
if err != nil {
    return err
}
return rt.Run(ctx)
```

`OptionsFromEnv` writes structured logs to the writer you pass, in the format that
`ENGINE_LOG_LEVEL` and `ENGINE_LOG_FORMAT` select. You can change any field of the
returned options before you call `runtime.New`, or build `runtime.Options` by hand.

`runtime.New` validates the database URL and the supplied registries, but it does not
connect to Postgres. `Run` opens the engine pool, publishes the registered definitions
to `engine.definition_catalog`, then starts the workflow worker, activity worker,
maintenance worker, and projector until the context is cancelled.

If `ProjectID` is set, `Run` verifies that the platform project exists before workers
start. Create the project first and set `ENGINE_PROJECT_ID`; see
[Engine project provisioning](/guides/engine-project-provisioning).

See `engine/examples/worker-template` for a minimal, copyable program with signal
handling and a workflow unit test.

## Retention

The runtime periodically bounds finalized engine journals and request-dedupe rows. The
`ENGINE_RETENTION_TERMINAL_RUNS` / `runtime.Options.RetentionTerminalRuns` window
defaults to `168h`, `ENGINE_RETENTION_DEDUPE_GRACE` /
`runtime.Options.RetentionDedupeGrace` defaults to `24h`, and
`ENGINE_RETENTION_BATCH_SIZE` / `runtime.Options.RetentionBatchSize` defaults to `500`.
For environment configuration, a retention window of `0` disables that class. In Go
options, leave a window at `0` to inherit its default or use a negative duration to
disable it.

After terminal-run retention, the projected trace and its root span remain available in
the debugger, but the engine history journal, inbox rows, and activity tasks for the run
are deleted.

## Pool and workflow limits

The engine pool defaults to 10 maximum connections, 2 minimum connections, a `1h`
maximum connection lifetime, a `30m` maximum idle time, and a `1m` health-check
period. Configure them with `ENGINE_DB_MAX_CONNS` / `runtime.Options.DBMaxConns`,
`ENGINE_DB_MIN_CONNS` / `runtime.Options.DBMinConns`,
`ENGINE_DB_MAX_CONN_LIFETIME` / `runtime.Options.DBMaxConnLifetime`,
`ENGINE_DB_MAX_CONN_IDLE_TIME` / `runtime.Options.DBMaxConnIdleTime`, and
`ENGINE_DB_HEALTHCHECK_PERIOD` / `runtime.Options.DBHealthCheckPeriod`.

The projector processes up to 1000 rows per poll by default; use
`ENGINE_PROJECTOR_BATCH_SIZE` / `runtime.Options.ProjectorBatchSize` to change it.
Child workflow nesting and continue-as-new following both default to 32 levels. Use
`ENGINE_MAX_CHILD_DEPTH` / `runtime.Options.MaxChildDepth` and
`ENGINE_MAX_CONTINUATION_FOLLOW_DEPTH` /
`runtime.Options.MaxContinuationFollowDepth` to configure those limits. Positive Go
option values override environment-derived values and defaults. To configure zero
minimum pool connections from Go, set both `runtime.Options.DBMinConns` to `0` and
`runtime.Options.DBMinConnsSet` to `true`.

## Start runs

The embedded process executes runs for definitions it registered. Start those runs
through `POST /v1/engine/runs` on the platform server, or with the Python
`EngineControlClient`. The definition name and version must be in the catalog that a
running worker published. `continua-engine start` cannot start your definitions: it
resolves only the built-in demo definitions on a fixed demo project. See
[Run your own workflows](/guides/run-your-own-workflows) for the request.

## Scope and caveats

- The runtime is preview and not a production-ready multi-tenant worker host.
- Workflow and activity authoring is Go-only.
- There is no dynamic definition loading path yet; user code registers definitions in
  the Go process at startup.
- All workers on one engine database must register the same definitions. A runtime
  start replaces the shared definition catalog, and a worker fails a claimed run whose
  definition it does not register. See [Run your own workflows](/guides/run-your-own-workflows).
- A scoped runtime requires a pre-created platform project. Missing projects fail startup
  instead of creating implicit projection rows.
- The runtime uses the same Postgres-backed history, leases, timers, signals, activity
  tasks, child workflows, cancellation, continue-as-new, and projection path as
  `continua-engine serve`.
